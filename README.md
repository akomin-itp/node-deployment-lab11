# Deployment API Lab — практична робота №11

Express API для відпрацювання конфігурації, CI та публікації. Серверна частина й тести готові; роботу виконуйте за методичкою.

## Початок

Потрібні Node.js 24, npm та Git. У каталозі з package.json виконайте:

```sh
npm ci
npm test
```

Далі доповніть scripts у package.json (P1), .env.example (P2) та workflow (P3). Створіть локальний .env за зразком. Команди start і dev мають бути додані за кроком 2 до першого запуску. Під час перевірки оновлення змінюється лише version у src/release.js.

## Маршрути

- GET /health — 200, HTTP-процес відповідає.
- GET /ready — 200, готовність API; зовнішніх залежностей немає.
- GET /api/v1/info — 200, service, nodeEnv, environment, message, version, revision.
- Невідомий маршрут — 404, error.code: ROUTE_NOT_FOUND.

## Параметри

PORT — порт процесу (за відсутності 3000); NODE_ENV — режим бібліотек; APP_ENV — development, staging або production; APP_MESSAGE — безпечний текст у відповіді. DEPLOY_REVISION можна передати для ручного розгортання. Якщо його немає, використовується RENDER_GIT_COMMIT, потім local. Значення version береться з src/release.js.

API слухає 0.0.0.0. Звичайний npm start після додавання script читає вже передані змінні й не завантажує .env. У хмарі параметри задають у налаштуваннях сервісу. Для локального запуску dev використовує --env-file=.env.

## Готова перевірка API

```sh
node scripts/check-api.mjs http://localhost:4100 1.0.0 staging
```

Сервер має бути запущений з NODE_ENV=production і APP_ENV=staging. Для публічного сервісу замініть адресу та використайте production. Після зміни release.js перевіряйте 1.1.0. За потреби четвертим аргументом задайте очікуваний повний revision. Сценарій перевіряє чотири маршрути, статуси, JSON, версію й середовище; помилка дає ненульовий код завершення. Максимальний час очікування одного запиту — 120 секунд.

## Безкоштовне виконання

Основний варіант — Render Free та GitHub Actions у публічному репозиторії зі стандартним ubuntu-latest. Платні ресурси й картка для виконання роботи не потрібні. Якщо продовження вимагає оплату або картку, використовуйте описаний у методичці резерв: Codespaces лише в межах включеної квоти, або локальний запуск за недоступності безкоштовної хмари. Тимчасовий доступ Codespaces не слід називати постійним production-хостингом.

.env і node_modules не додавайте до Git. Не вводьте секрети у APP_MESSAGE: це поле повертається публічно. Після виконання видаліть тимчасовий Codespace; він використовує квоту сховища навіть у зупиненому стані.
